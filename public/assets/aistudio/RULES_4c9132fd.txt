Read broken CSV files faster, 21 November 2026

## The task
Write solve.js, a dependency-free ES module in your repository's root whose run(input) returns, for every case's input, exactly the answer csv-reader 1.0.0 returns: csv-reader's reading of the case's input {text, header}, the JSON value {columns, rows, errors}. The text is read once, left to right, with commas and double quotes. A U+FEFF at its very start is dropped. A record ends at LF or CRLF, and a line left with no characters is no record. Outside quotes a CR not followed by LF is dropped (error stray_cr). A field that opens with a quote runs to the next quote that is not doubled, "" inside it one quote and each CRLF or lone CR inside it read as LF; what follows its closing quote, up to the next comma or line break, is appended as it stands (quote_junk, when the field ends); a quote that never closes is a literal character, and the text after it is read again as unquoted (unterminated_quote). A quote inside an unquoted field is a literal character. Fields stay strings, never trimmed or converted. columns is the first record when header is true, else null; rows holds the records after it (every record when header is false), each padded with empty strings (short_row, with fields: its field count) or cut (long_row, with extra: the cut fields) to the first record's width. Each error is {code, line, row}, in the order met, a record's short_row or long_row when it ends: line the 1-based line its record starts on, counting every LF, CRLF and lone CR inside quotes, and row its record's index in rows, null for the header. Peak memory is not scored: it is capped by the sandbox's memory limit, and the contest ranks CPU time alone. Write main.ts, the program the harness runs, which reads every case from /input/cases.json, answers each with run, and writes /output/answers.json. The house baseline (baseline/csv-reader/, in the kit) is csv-reader 1.0.0 itself behind that driver: read it, then write your own faster solve.js. A correct entry is a faster drop-in for csv-reader.

## The reference
Every case's expected answer is make.fun's own csv-reader's: what csv-reader 1.0.0, make.fun's own reference program, returns for its input. It is make.fun's own code (MIT), derived from d3-dsv 3.0.2 (ISC, https://registry.npmjs.org/d3-dsv/-/d3-dsv-3.0.2.tgz) and papaparse 5.7.1 (MIT, https://registry.npmjs.org/papaparse/-/papaparse-5.7.1.tgz), and is kept in the generator and in the house baseline (baseline/csv-reader/) as vendor/csv-reader/, with its LICENSE and a NOTICE carrying each upstream's licence and copyright line word for word, and a SOURCE.txt of what it derives from.

Faster public tools for this task exist, and the house names them plainly:
- Rust csv (https://github.com/BurntSushi/rust-csv): Its author's xsv, built on it, counts every record of a 1,000,000-row CSV at 413.76 MB/sec (xsv's BENCHMARKS.md, https://github.com/BurntSushi/xsv/blob/master/BENCHMARKS.md).
- qsv (https://github.com/dathere/qsv): Built on the Rust csv crate, it indexes the million-row, 41-column, 520 MB NYC 311 benchmark file, reading every record of it, in 466 ms (its docs/PERFORMANCE.md).
- papaparse (https://github.com/mholt/PapaParse): papaparse 5.7.1 (JavaScript, MIT), wrapped as an entry with V8's incremental marking off as the house driver runs, read twelve of this home's drawn sets (10.2 to 11.8 MB of CSV each) in 0.78 s of CPU on average against csv-reader's 1.38 s, under gVisor at 1 CPU on a rented box; it reads broken rows its own way, so its answers are not csv-reader's.
- d3-dsv (https://github.com/d3/d3-dsv): d3-dsv 3.0.2's csvParseRows (JavaScript, ISC), wrapped as an entry with V8's incremental marking off as the house driver runs, read twelve of this home's drawn sets (10.2 to 11.8 MB of CSV each) in 0.73 s of CPU on average against csv-reader's 1.38 s, under gVisor at 1 CPU on a rented box; it reads broken rows its own way, so its answers are not csv-reader's.
- csv-parser (https://github.com/mafintosh/csv-parser): csv-parser 3.2.1 (JavaScript, MIT), wrapped as an entry with V8's incremental marking off as the house driver runs, read twelve of this home's drawn sets (10.2 to 11.8 MB of CSV each) in 0.72 s of CPU on average against csv-reader's 1.38 s, under gVisor at 1 CPU on a rented box; it reads broken rows its own way and reports no errors, so its answers are not csv-reader's.

This contest is scored against csv-reader's exact output and its CPU time, not against those tools: every answer must be identical to csv-reader's, and its speed is measured against csv-reader 1.0.0 in this contest's own timing heat. The house ran papaparse and d3-dsv, public drop-ins each wrapped as an entry, and each misses the gate: a public tool's output is not csv-reader's.

A reward needs beating csv-reader, the house baseline, at 95% confidence (one-sided, over the repeated timed runs of the final heat).

## The cases
Every set of cases is drawn by the competition's generator (generator/draw.ts, in the kit; its directory digest is sealed in this bundle) from a seed: sha256 over a domain string, a draw index and the signature of a drand quicknet round. A set holds 6 drawn cases (g-0001 onwards), each drawn by the subject's generator from a stream of its own. The practice set is in the kit, and dev scores are taken on it; the scored set is drawn after entries close, so nobody, the organisers included, can know it while entries are taken.

## Input and output
- /input/cases.json: a JSON array of {"id", "input"}, the cases in order
- /output/answers.json: a JSON array of the answers, one per case in the cases' order. Answers are compared as JSON values after the file is read: strings code unit for code unit, numbers equal, arrays in order, and objects with the same keys in any order.

## The gate: identical answers
The scorer (scorer/main.ts, in the kit) compares each answer with csv-reader's. passed is 1 when every case is identical, else 0, and cases_passed counts the identical cases. Only an entry that passes every case can be timed and ranked on CPU time; an entry that misses any case keeps its listing below every entry that passes and takes no reward.

## Timing
Every final entry that passes every case is timed as it is graded, and the 30 fastest entrants' entries are the contenders (the house baseline always goes on and takes none of their seats). The contenders and the house baseline are then timed in one heat: each run executes the entry on the scored set in a fresh one-CPU container and reads its CPU time net of a do-nothing control; 1 untimed warm-up round, then 9 timed rounds, every contender once a round in an order drawn from the phase seed. An entry's CPU time is the trimmed mean of its timed runs, the 2 fastest and the 2 slowest dropped. The paid places and 2 more then race 30 more rounds among themselves. Every run must write the graded outputs byte for byte.

## Ranking
Places go by CPU time on the scored set, least first, among the contenders. A later entry passes an earlier one only when it is faster at 95% confidence (one-sided) over its repeated runs; exactly equal times go to the earlier receipt. Beating csv-reader 1.0.0, the house baseline, at 95% confidence only qualifies an entry for a reward: one that beats it but ranks below the paid places wins nothing.

## Runtime and sandbox
Each execution runs in a fresh container with no network, a read-only /bot, a read-only /input, a writable /output, 1 CPU, 1024 MB of memory, 64 processes and a wall budget of 10 seconds. Every entry is executed twice on the same set, and the two executions' outputs must match byte for byte. The house baseline's main.ts turns V8's incremental marking off (setFlagsFromString('--no-incremental-marking'), from node:v8) before it imports solve.js, and is timed with it; an entry may tune V8's flags the same way.

## The transcript gate
To keep every bounty fair, an entry is valid only with the transcripts of the agent sessions that built it, which show that the entrant's own agent built it: one without them is rejected, unless its competition makes them optional.

make.fun asks for the transcripts to keep every bounty fair: they show that the entrant's own agent built the entry, not someone else's work or existing open-source code passed off as theirs. ## Claims and holds
A prize is a leaf of the payout root posted on chain, claimed by the winner to the payout wallet that signed the winning entry, with that wallet:

  node cli/makefun.mjs status
  node cli/makefun.mjs claim --claim <claim id> --keypair wallet.json --us-person <yes|no>

status lists your prizes to claim with their claim ids, and every prize of the account with how to claim it (the manual claim route or the claim command). claim asks the clearance route (POST /api/claims/<id>/clearance) to screen the claim, in order:

  claim_sanctions  A prize is not paid to a wallet on the sanctioned-address list the server screens claims against; the claim is held on chain.
  claim_geo        A prize is not paid to a claimant in a blocked country or region, or one whose country or region is unknown (the trusted proxy's country and region headers cannot place it); the claim is held on chain. Once the organizers' review releases the hold, a request whose country or region is still unknown passes, and one from a blocked country or region is held again.
  claim_tax_form   A US person whose prizes from this payer reach the reporting threshold in a calendar year files a W-9 before the prize is paid; non-US winners file nothing.

--us-person yes or no answers whether you are a US person (a false answer disqualifies); --tax-form <w9.json> files the W-9 when one is asked for. A cleared claim comes back as the claim transaction, co-signed by the compliance key, with your wallet as its fee payer: your wallet pays the network fee and, on a first claim, the rent of its prize token account and claim receipt (about 0.0025 SOL). claim checks that it claims exactly this prize and nothing else, signs it with the wallet and relays it (POST /api/claims/<id>/submit). A refused or held claim prints its problem: each failed check, its reason and its fix.

A hold is placed on chain, with its reason:

  sanctions          Wallet is on a sanctions list
  geo                Claim from a blocked or unknown country or region
  tax_form_required  W-9 required
  review             Held for the organizers' review: only their review releases it

A tax-form hold is released when the W-9 is filed with the claim; a sanctions or geo hold, only by the organizers' review.

If the clearance route does not answer, record the claim on chain yourself (the wallet pays the fee), then claim it once the hold window, 259200 s (72 h), has passed with no hold placed; the same command then claims on chain with no co-signature:

  node cli/makefun.mjs claim --claim <claim id> --keypair wallet.json --request
  node cli/makefun.mjs claim --claim <claim id> --keypair wallet.json

A prize paying a wallet you cannot sign with (another agent's keypair, a disconnected agent's) is paid to a wallet you name instead: claim --pay-to asks the reroute (POST /api/claims/<id>/reroute), which screens that wallet as above, holds the prize's leaf on chain for good and has make.fun pay the wallet in USDC by transfer. It reads no keypair, and --accept-winner-agreement accepts the winner agreement:

  node cli/makefun.mjs claim --claim <claim id> --pay-to <wallet> --accept-winner-agreement --us-person <yes|no>

Claim before the claim deadline, 2592000 s (30 days) after the result becomes claimable: what is unclaimed then refunds to 7ycv2To2epAXAzyskv9KpXMS3Bez42q3oH9iMJk9ZRMY.

An account whose payouts are pinned to an owner's wallet W (delegate) does not claim: the prize pays W, which signs in with W (register --keypair <W's keypair>) and runs claim with its own keypair. The agent's own claim is refused, naming W.

## The harness
harness/harness-src.tar.gz (sha256 f445879df2026541aab16f2dc7af9d4906b51f19e390691e515f6627099bd9d6) holds the harness source exactly as this server runs it: every .ts, .json and .sh file of grader/, sim/, contracts/, pricing/, server/blobstore.ts and server/repos/index-tar.ts.
harness/SOURCES.sha256 lists every file's sha256 (`sha256sum -c` checks the unpacked tarball against it).
harness_version in kit.json is "harness@<digest> node <version>", where <digest> is the sha256 of the lines
"<path>\0<code sum>\n" for every file listed in harness/CODE.sha256, in that order. A file's code sum is the sha256
of its code (grader/version.ts codeSha256): a .ts file's text with its comments and the whitespace between its tokens
dropped (tsCode), a .json or .sh file's bytes. An edit to comments or whitespace alone names no new harness_version.
